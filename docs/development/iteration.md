# 轻量迭代方法

2026-10-03 经用户确认。目标是尽快交付可使用的业务流程，并让新会话能接续工作。工程边界见 [AGENTS.md](../../AGENTS.md)，本页集中说明执行方式。

## 一批工作怎样完成

每批选择一个可验证的业务流程，或 1～3 个紧密相关的问题。先复核相关历史失败和原型差距，再确定验收条件；无须完成全模块穷尽回归才开始修复。

1. **复现与对照**：记录当前提交和相关场景，对照归档 mock 页面；区分缺陷、缺失能力、展示差异和规则疑问。
2. **确定本批目标**：在模块工作说明中填写目标、关联编号、验收条件，以及必要的实现和测试步骤。已有明确目标可直接执行，不重复申请计划批准。
3. **开发与验证**：从最小相关改动开始，完成前后端联调，验证原失败用例及直接受影响场景，处理本批引入的问题。
4. **交接与集成**：提交可恢复检查点，更新总表及模块说明。按约定集成到主分支，在实际集成版本验证受影响流程；向用户说明结果和剩余问题。

常规技术决策自主完成，持续执行到本批可验收。新发现的无关问题登记后安排下一批，不无限扩大当前范围。业务规则不明时提出具体决定及建议，继续处理不依赖该决定的工作。

## 需求、问题与设计放在哪里

| 载体 | 唯一职责 |
| --- | --- |
| [需求与问题总表](../testing/role-regression-issues.md) | 编号、类型、优先级、当前状态、问题或需求、验收条件、最新验证与提交引用 |
| 每模块一份工作说明 | 原型与代码入口、本批目标与短计划、最新结果、下一步；通过编号引用总表，不复制问题状态 |
| 必要的设计说明 | 涉及重要状态流转、数据结构、权限或跨模块方案时，在 `docs/design/` 保存难以用几行说明的决策，并从任务链接 |

普通修复把设计理由和测试步骤写在任务或模块说明中，不拆成 PRD、设计、开发计划、测试计划、验收报告和交接报告。专项报告只用于较大回归或需要独立保存的结论；既有报告保留为历史证据。

总表保留已有 `REG-*` 编号，新增问题递增分配；新增需求使用 `REQ-*`。创建前检查是否已有同一根因，并在集成时处理并行编号冲突。合规考核项保留严重性，执行状态设为暂缓。

状态为：**待处理 → 进行中 → 待验收 → 已完成**，另设**暂缓**。

- 待验收：本批实现和技术验证已有结论；注明是否已集成，以及仍需用户确认的业务或页面效果。
- 已完成：对应验收条件满足，目标集成版本已验证；需要用户确认的事项已确认。用户预先授权自动验收时，按约定标准完成并记录依据，不额外增加确认轮次。
- 暂缓或受阻：说明原因和恢复条件；受阻说明直接记在当前条目，不另建状态系统。复验失败保留旧结果，退回进行中或待处理。

任务信息够用即可：`编号 / 类型 / 模块 / 优先级 / 状态；目标或复现；验收条件；参考；最新验证和提交`。不重复复制关联报告中的长日志。

## 原型与业务决定

依据顺序为：用户最新确认要求 → 已确认规则与验收标准 → 原 mock 页面 → 当前实现。mock 页面是最终布局与交互的重要参考，不能直接替代权限、状态流转和数据一致性规则。

- 原型普通遗漏由开发补齐并简记理由；重要业务规则或明显改变已确认操作习惯时，由用户决定。
- 决定写入关联条目或必要设计说明，记录结论和原因；不另外维护重复的决策台账。
- 档案保持只读。不能以原型占位按钮、假数据或当前实现为由，宣称真实能力已经交付。

## 模块与会话

| 会话入口 | 负责范围 | 初始关注点（待复核） |
| --- | --- | --- |
| [案件管理](../modules/cases.md) | 总部、业务部门、外聘律师案件流程 | 协查办理、律师授权与身份映射、任务提交 |
| [合规检查](../modules/inspections.md) | 总部和分支的检查、报告、整改 | 附件权限、正常闭环、状态与待办一致性 |
| [系统管理](../modules/system.md) | 身份、组织、权限、字典、公共能力 | 管理操作事务边界、字典重复值、公共依赖 |

合规考核暂缓新功能与专项修复。公共改动直接影响它时做必要兼容性冒烟，不扩展为考核优化任务。

### 代码与集成

- 各会话使用独立 worktree 和任务分支，如 `work/cases-<主题>`；复用适合的现有工作区。主工作区负责集成与演示，无须另建专门协调会话。
- 启动时记录基线提交和负责范围。共享认证、字典、数据库迁移、导航及跨模块文件须指定一个负责会话；按功能归属协调，不能仅凭目录划分。
- 合规检查与考核共用 `compliance-shared` 等实现，修改前查看直接使用方。系统管理负责公共能力协调；已明确交给其他会话的局部公共修复可由该会话完成。
- 集成者每次合入一个批次，核对新增条目编号、冲突和公共接口兼容，运行受影响检查。未经集成的模块分支不称为主版本已交付。
- 提交和推送遵循当前用户授权；不覆盖其他会话修改，不强推共享分支。模块分支准备集成时同步最新主线，避免为保持实时同步反复打断开发。

### 共享本地环境

当前脚本使用固定 Compose 项目名 `compliance-evaluation-dev` 及共享端口、镜像配置。worktree 不隔离服务、数据库和测试数据。

- 可以并行分析、编码和执行不依赖共享服务的测试；部署、迁移、重启及共享环境联调必须依次进行。
- 联调前在主工作区忽略的 `.local/shared-environment.md` 记录使用会话、工作区、部署提交和预计操作，结束后标明释放及当前部署提交。这是协作记录，不是原子锁；出现多个申请或状态不清时先协调，不能直接重启。
- 统一从约定工作区部署；记录实际运行的提交，避免用自己的源码解释另一版本的测试结果。使用按模块和批次区分的测试数据标记。
- 新 worktree 不自带忽略的 env、测试凭据及归档索引。按需从已有本地配置恢复引用，不把它们提交，也不盲目重新 bootstrap 或重置 Casdoor。
- 日常停止保留数据卷。以后确需同时联调，再隔离 Compose 项目名、端口、镜像、数据库/卷及相关配置；本规范不表示已经完成隔离。

## 验证与验收

| 风险与改动 | 最小有意义的验证 |
| --- | --- |
| 文档 | 内容、路径与链接、差异和发布检查；不重跑写数据的业务回归 |
| 文案、间距、展示 | 受影响页面的实际效果，必要时构建；不编写机械复述实现的测试 |
| 表单与增删改 | 主流程、关键错误输入、保存后独立读回，覆盖相关角色 |
| 状态流转 | 合法路径、禁止操作及上下游状态一致性 |
| 权限、文件、公共能力、数据库 | 真实允许与拒绝、资源范围、受影响模块；按改动补充一致性、迁移和失败回滚检查 |
| 持久化或内存工作集 | 新增/修改后的读回；改变持久化行为时验证重启读回 |

以实际运行结果验收，不凭构建通过或 HTTP 200 关闭业务缺陷。历史失败和类型诊断单独标明，只修本批相关问题，不要求无关任务先清空全部历史欠账。发现新增失败须定位与本批的关系。

公共接口、授权和复杂状态变更进行重点代码复查；无需为每次小改动强制多代理评审。UI 变化在有助于判断效果时留代表性截图，不为每一步生成证据包。

每批交付简要说明：**改了什么、验证了什么、剩余问题、提交与集成情况、下一步**。技术验证完成与用户验收完成分别说明。详细日志和截图留在忽略的 `.local/`，提交文档不得含密码、token 或敏感响应。

## 新会话启动提示

替换模块名称和入口即可使用；此模板不自动创建会话或授予未声明的发布权限。

```text
继续 compliance-evaluation 的【模块名】迭代。
遵循 AGENTS.md 和 docs/development/iteration.md，读取【模块工作说明路径】。
检查当前分支、未提交修改和模块交接；使用独立 worktree/分支。
先复核当前批次相关问题，对照原始 mock 页面评估差距，完善必要业务规则。
每批完成一个业务流程或 1～3 个相关问题，连续执行到可运行、可验证。
常规问题自行处理；业务规则、权限边界等重大决定再提出具体建议。
共享 Docker 联调先协调使用窗口；合规考核暂缓。
更新统一问题总表和模块交接，保存提交，报告验收结果与下一步。
```

## 方法来源

本规范是项目选择的工作方式，参考了 OpenAI 的 [GPT-6 Astra 技能与提示实践](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)、[AGENTS.md](https://developers.openai.com/codex/agent-configuration/agents-md)及 [Worktree](https://developers.openai.com/codex/environments/git-worktrees)说明。按任务读取上下文、明确完成标准和自主边界；不规定必须切换模型或引入新的流程框架。
